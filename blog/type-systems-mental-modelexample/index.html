Type Systems as a Mental Model

2025-01-28
programmingtype-theory

I used to think of types as the compiler being annoying. Now I think of them as documentation that can’t get out of sync with the code.

The Key Insight#

When you write:

function fetchUser(id: string): Promise<User | null> {
  // ...
}

You’re not just satisfying the compiler. You’re telling every future reader:

  • This function takes a string ID
  • It returns a promise
  • The user might not exist

That’s three pieces of documentation that are always accurate, because the compiler enforces them.

Types as Design Tools#

The real power isn’t in catching bugs — it’s in designing your data model. If you can’t represent an invalid state in your types, you can’t have that bug at runtime.

// Impossible to have a "loading" state with an error
enum LoadingState<T> {
    Loading,
    Loaded(T),
    Error(String),
}

When Types Get in the Way#

There are legitimate cases where strict types slow you down:

  • Prototyping and exploration
  • Highly dynamic data (like JSON from external APIs)
  • One-off scripts

The trick is knowing when the investment in types pays off. For code that will be maintained by more than one person, or live longer than a week — types almost always pay for themselves.
