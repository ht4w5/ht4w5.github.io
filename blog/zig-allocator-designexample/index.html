Zig's Allocator Design Is Clever

2025-03-01
zigprogramming

One of Zig’s most interesting design decisions is making allocators explicit. Instead of a global malloc, every function that needs memory takes an allocator as a parameter.

The Pattern#

fn readFile(allocator: Allocator, path: []const u8) ![]u8 {
    const file = try std.fs.cwd().openFile(path, .{});
    defer file.close();
    return try file.readToEndAlloc(allocator, 1024 * 1024);
}

This looks verbose, but it has real benefits:

Testability#

In tests, you can use a FixedBufferAllocator that detects leaks and double-frees:

test "readFile allocates and frees correctly" {
    var buf: [1024]u8 = undefined;
    var fba = std.heap.FixedBufferAllocator.init(&buf);
    const data = try readFile(fba.allocator(), "test.txt");
    // No need to free — the buffer allocator handles it
    _ = data;
}

Control#

In production, you choose the allocator based on context:

  • GeneralPurposeAllocator for safety
  • ArenaAllocator for batch allocations
  • PageAllocator for large allocations
  • Custom allocators for specific patterns

The Trade-off#

It’s more typing. Every function signature that allocates needs the allocator parameter. But the payoff is code where you can see where memory comes from, which makes leaks and use-after-free bugs much easier to find.

It’s a different philosophy from Rust (ownership at the type level) and C++ (RAII), but it’s surprisingly effective.
