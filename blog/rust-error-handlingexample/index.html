Error Handling in Rust: Beyond Result<T, E>

2025-03-10
rustprogramming

Rust’s approach to error handling is one of its most distinctive features. Unlike exceptions in C++ or Java, Rust uses return values to signal errors, which forces you to handle them at the call site.

The Problem with unwrap()#

We’ve all been there — prototyping code littered with unwrap() calls. It works until it doesn’t, and then your program panics in production.

// Don't do this in production
let file = File::open("config.toml").unwrap();

Custom Error Types#

For real applications, you want structured errors:

#[derive(Debug)]
enum AppError {
    Io(std::io::Error),
    Parse(toml::de::Error),
    MissingField(String),
}

impl std::fmt::Display for AppError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            AppError::Io(e) => write!(f, "IO error: {}", e),
            AppError::Parse(e) => write!(f, "Parse error: {}", e),
            AppError::MissingField(field) => write!(f, "Missing field: {}", field),
        }
    }
}

The ? Operator#

The real magic is the ? operator, which propagates errors up the call stack while keeping your code clean:

fn load_config() -> Result<Config, AppError> {
    let contents = std::fs::read_to_string("config.toml")?;  // auto-converts io::Error
    let config: Config = toml::from_str(&contents)?;          // auto-converts parse error
    Ok(config)
}

This is one of those features that feels obvious in retrospect but took real design effort to get right.
